# R01 — стабілізація HEOS і перевірка виконання

Підсумок **21.10.2026**. Розпочато після [контрольної копії R00](../development-r00/REPORT_UK.md).
Кандидат цього етапу: **1.39.0 / f16d46d30b5e**, без публікації.
Наступний локальний кандидат і докази перенесення турбіни/flash описані
в [доповненні R01](STEAM_PROCESS_WORKER_UK.md).
[Точні результати та хеші](acceptance.json). R01 залишається відкритим для
повного приймання інших допоміжних форм; цей звіт фіксує завершені підзадачі.

## Що виправлено

1. **IAPWS-95 на Node 24.** Насосна ділянка незалежного dry-saturated-inlet
   прикладу Ренкіна відмовляла при пошуку густини холодної рідини. Встановлений
   проблемний стан: p = 0,029138033297768044 MPa, T = 273,1578814055549 K.
   Після зупинки Ньютона резервний інтервал міг потрапити в нефізичні гілки EOS.
   Тепер пошук зберігає стабільні проби з обох боків кореня; при малому кроці
   біля машинної точності перевіряє локальні проби поза невдалим демпфуванням.
   **Допуск тиску не розширено.** Вісім незалежних Python iapws 1.5.5 станів
   перевіряють густину, h/s, cp/cv, звук та фактичний залишок рівняння тиску.
2. **Спільний CoolProp після аварії.** Непередбачений нативний виняток HEOS
   блокує весь пошкоджений WASM, включно з вологим повітрям і реальними газами.
   Worker замінюється; для спільного ядра сторінки потрібне перезавантаження.
   Повторних нативних викликів немає. Повідомлення про відновлення перекладено;
   незалежний IF97 залишається працездатним.
3. **Фактичний запуск аудиту у Windows.** `audit-inverse-precision.mjs`
   порівнював нативний шлях з URL pathname і міг повернути 0 без розрахунків.
   Використано `fileURLToPath`; новий CLI-тест вимагає звіт із виконаними
   реальними випадками. Повний запуск тепер підтвердив 4657/4657 запитів.
4. **Перший показ HEOS-результату.** Опорний стан для ексергії обчислюється
   в уже наявному розрахунковому Worker, а не першим запитом властивостей у
   головному потоці під час render. Кеш обмежено 32 станами й прив’язано до
   точних P₀/T₀. Відновлення/імпорт готують опорний стан через project Worker;
   зміну довкілля можна скасувати, редагування не застосовує застарілі параметри.
   Формула ексергії, моделі та система відліку h/s збережені.

## Числові й програмні перевірки

- Node **22.23.3** і **24.18.1**: по **1795/1795** модульних тестів, без пропусків.
- Повний незалежний аудит на Node 24: **2200 станів, 4657 запитів, 0 відмов,
  0 розбіжностей**; IF97 — 3439, IAPWS-95 — 1218. Після цього змінено UI-код
  `app.js`; хеші всіх чисельних JS-джерел аудиту збережені. Поточний core також
  повторив власні водяні, HEOS і транспортні перевірки.
- Поточна HEOS-матриця: **595 викликів**; 582 збіги, 6 допустимих
  неоднозначностей і 7 випадків обумовленості інверсії, 0 відмов.
- Чотири окремі процеси зі справжнім C++-винятком: low-level, high-level,
  перехоплення помилки всередині batch та спільний контекст сторінки.
- Chromium **151.0.7922.34** та Firefox **153.0**: по **8 груп** аварійного
  сценарію. Перший результат і зміна P₀/T₀ збігаються з незалежною ексергією
  Python iapws, коли тест забороняє `PropsSI`/`factory` у головному потоці.
  Перевірено редагування й скасування незавершеного опорного стану, справжній
  C++-збій, відсутність повторних викликів, незмінену історію, обидві мови,
  роботу IF97 та відновлення HEOS після reload.
- В обох браузерах повторено **8 груп основного workspace**: 12 знімків
  результатів, змішані моделі/проєкти, відмова підроблених результатів, серії,
  ручний корінь, діаграми, HEOS-процес і Ренкін. Повне закриття профілю та
  відключення сервера/мережі відтворили проєкт, корінь і HEOS-цикл офлайн.

Перший core-запуск має **19/20** успішних перевірок: P09 не знайшов `python3`
у Windows, хоча інший Python уже був явно налаштований. Додано fallback
`P09_PYTHON → REFERENCE_PYTHON → REACTOR_PYTHON → python3` та явну діагностику
помилок запуску. Окремий повтор P09 пройшов: **600 перевірок**, з них 406
числових і 194 очікувано відсутніх значення; максимальна відносна похибка
перетворення 3,262×10⁻¹⁶. Отже, всі 20 індивідуальних перевірок мають успішні
докази, але **початковий core report залишається failed**. Це не новий
суцільний зелений релізний прогін; такий прогін належить R02.

Повторюваність збірки/ZIP та цілісність пакета в цьому core пройдені.
Зелений програмний результат не змінює `physical-screening-failed`
наявної нейтронної моделі й не доводить відповідність Steam97Web.

## Спостережена реакція інтерфейсу

Незмінені зібрані assets, один ПК AMD Ryzen 7 5700G, headless Chromium/Firefox,
loopback, свіжий контекст без throttling; Service Worker у цьому вимірюванні
вимкнений. Таймер 20 ms спостерігає затримки головного потоку.

| Перший HEOS-розрахунок | До, build 9c6a119917fd | Після, build f16d46d30b5e |
| --- | ---: | ---: |
| Chromium: максимальний проміжок таймера | 2296 ms | 50,3 ms |
| Chromium: час до результату | 4862,5 ms | 2651,1 ms |
| Firefox: максимальний проміжок таймера | 13 114 ms | 38 ms |
| Firefox: час до результату | 26 877 ms | 13 582 ms |

Повільна перша підготовка даних Water у Worker лишилася, але більше не дублюється
головним потоком для показу ексергії. Це одиничні вимірювання кожного сценарію,
не статистично підтверджений коефіцієнт прискорення й не обіцянка для інших ПК.
Запропонований бюджет проміжку ≤1000 ms у цих двох UI-сценаріях виконано.

**Уточнення методики:** швидкий вибір радіокнопки не вимірює перший розрахунок.
Прямий діагностичний виклик `mainHeosInitialization` включав і підготовку модуля,
і перший запит властивостей Water. Початковий висновок, що вся довга пауза
спричинена спостерігачем WASM, не підтвердився: незмінений UI окремо відтворив
її під час першого результату. Висновок про виправлення спирається на наведені
реальні UI-прогони, а не на різницю між селектором та діагностичним API.

## Пам’ять і скасування: межі доказів

До перенесення UI-опорного стану виконано по 30 циклів cancel/recreate у
Chromium і Firefox: після кожного повтору отримано правильний HEOS-стан;
у контрольних знімках залишався один активний Worker. Зібрані 100/500-точкові
серії та ємності WASM. Цей діагностичний сценарій навмисно викликає Water також
у головному потоці й не є виміром нового звичайного UI-шляху.

WASM-ємність — виділена лінійна пам’ять, не обсяг живих об’єктів. CDP JS heap
стосується головного frame; Windows private bytes — commit процесів, не
фізична RAM. Знімки не є вичерпним піком. Для Firefox CDP-метрик немає —
відсутність позначена як null, а не нуль. Обмежена серія не доводить повної
відсутності витоків. Перша Firefox-спроба була перервана без прогрес-логу;
пізніший повний 30-кратний сценарій завершився. Переривання не є доказом
зависання обчислювача.

## Що робити наступним

1. Завершити R01: виміряти решту синхронних HEOS-форм і діаграм, узгодити
   бюджет холодного запуску й пам’яті. Прибирати підтверджені блокування
   конкретних сценаріїв через Worker; модель і нулі h/s не змінювати.
2. R02: повний релізний прогін одним кандидатом, усі браузерні сценарії,
   формати експорту, оновлення PWA, CI/Pages і перевірка опублікованої збірки.
   Поточні локальні докази не оголошувати вже виконаною публікацією.
3. За відсутності доступної обов’язкової задачі Steam97Web — R16, повний
   дедуплікований реєстр ht/fluids, потім R17 LMTD/ε–NTU. Нові двигуни
   chemicals/thermo/Cantera починаються з дослідних контрактів.

Фізичні Android/iOS і Safari залишаються R13; 390 px не замінює пристрій.
Повне приймання всіх допоміжних форм, поточний повний browser-release та
числовий паритет оригіналу ще не завершені. У Steam97Web нових чисел немає;
[початковий архів](../steam97-reference/README_UK.md) містить тільки блокування
доступу й наші історичні результати.

Для відтворення: `node --test tests/*.test.mjs`,
`node scripts/audit-inverse-precision.mjs`,
`node scripts/check-water-heos-fault-browser.cjs`,
`node scripts/check-water-heos-workspace-browser.cjs` та
`node scripts/benchmark-heos-selection.cjs`.
Браузерні сценарії повторюються з `BROWSER_NAME=chromium` і `firefox`;
локальний шлях Playwright задається `PLAYWRIGHT_MODULE_PATH`.
Вимірювання «до» використовує збережену збірку через `HEOS_SELECTION_ROOT`.
Генератори незалежних даних і pinned Python-оточення наведено в `sourceHashes`
машиночитного звіту; вони не імпортують код продукту.
