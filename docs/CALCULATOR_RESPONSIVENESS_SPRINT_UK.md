# Спринт: основний калькулятор без зависань

Статус: реалізовано у робочій копії **1.25.0 / 411cc4eb8831**. Числове й цільове приймання Chromium/Firefox виконано. Firefox пройшов автономні сценарії через `file://` і PWA після перезапуску без мережі. Системний Chromium блокує `file://`; повний релізний прогін, Safari, фізичні мобільні пристрої та публікація ще не завершені.

## Мета та результат

Завершити щоденний сценарій основного калькулятора води й пари: введення → розрахунок → вибір стану → історія → діаграма → експорт → відновлення проєкту. Складні розрахунки мають залишати інтерфейс доступним і дозволяти скасування. Поточні фізичні моделі та числові допуски зберігаються.

Номер версії — **1.25.0**. Вихідне вимірювання IAPWS-95 при P=3 МПа і T=673,15 K: h–v близько 815 мс, u–v 633 мс, v–s 349 мс у Node.js на цьому середовищі. Це спостереження, а не гарантія швидкості на інших пристроях.

## Підтверджена вихідна проблема

У `src/app.js` основний `run()` викликає `calculate()` синхронно. Два `requestAnimationFrame` перед запуском дають намалювати повідомлення про обчислення, але не дозволяють взаємодіяти зі сторінкою під час самого розрахунку. У `docs/CALCULATOR_COMPLETION.md` зазначено можливе блокування інтерфейсу складними інверсіями IAPWS-95.

Перевіряємо 20 наявних режимів: `pt`, `ph`, `ps`, `hs`, `prho`, `trho`, `pv`, `pu`, `tv`, `tu`, `us`, `vs`, `hv`, `uv`, `th`, `ts`, `px`, `tx`, `satp`, `satt`. Для кожної моделі фіксуємо фактично підтримувані області; неприпустимі стани перевіряємо як очікувані помилки.

Раніше реалізовані підказки й функції спочатку перевіряємо. Зміни інтерфейсу робимо для відтворених проблем, а не повторюємо вже завершені спринти.

## Правила поведінки

1. Одночасно виконується один основний розрахунок. Повторне натискання або Enter не створює дублікати в історії.
2. Скасування зупиняє обчислення у worker, повертає керування та зберігає введення й історію. Наступний розрахунок працює без перезавантаження сторінки.
3. Зміна входів, моделі, режиму або імпорт іншого проєкту під час виконання робить відповідь старого запиту неактуальною. Вона не оновлює результат, історію чи автозбереження.
4. До завершення розрахунку попередній результат не позначається як актуальний і не експортується як результат змінених входів. Наявні записи історії залишаються доступними.
5. Помилка, скасування й перевищення ліміту виконання розрізняються. Вони не створюють нового стану в історії. Ліміт одного фонового запиту — 60 секунд. Він також застосовується до перевірки проєкту; довга історія зі складними інверсіями може його перевищити, при цьому оригінал зберігається для відновлення.
6. Насичення відображає обидві фази; неоднозначний розв'язок дозволяє явно вибрати стан. Символ «—» має пояснення і не означає нуль.
7. Фоновий виконавець не звертається до DOM або localStorage. Застосування результату й збереження залишаються відповідальністю інтерфейсу.
8. Якщо worker не вдалося запустити, показуємо зрозумілу помилку й можливість повторити запуск. Не повертаємо непомітно блокувальний розрахунок у головний потік.

## Технічні межі

- Числове ядро `calculate()` та його синхронний API для Node-тестів зберігаються; асинхронний адаптер вводимо для основного браузерного калькулятора.
- Знаходимо всі входи до основного розрахунку: форма, приклади, історія, відновлення та імпорт. Переходи на асинхронне виконання перевіряємо разом із викликами, які зараз очікують негайний результат.
- Worker отримує канонічні числа, режим, модель та ідентифікатор запиту; повертає стан, насичення, альтернативи або помилку. Форматування одиниць і локалізація залишаються в інтерфейсі.
- WASM та потрібні модулі математичного ядра ініціалізуються у worker. Ресурси беруться з локальної збірки, без CDN і нових зовнішніх сервісів.
- Вебзбірка включає версійований ресурс worker у SHA-256-перевірки, PWA-кеш і ZIP. Автономна збірка містить його код і необхідні дані всередині HTML.
- Для автономного запуску перевіряємо Blob worker та мінімально необхідну зміну `worker-src` у CSP. Не послаблюємо інші обмеження політики.
- Старі JSON-проєкти відкриваються; службові об'єкти worker й незавершені запити не серіалізуються в проєкт.

## Етапи

1. **Вихідні вимірювання.** Фіксуємо повільні контрольні входи, час виконання й поведінку сторінки; складаємо матрицю режимів та всіх запусків основного розрахунку.
2. **Фоновий виконавець.** Готуємо worker-збірку й протокол; звіряємо результати з наявним синхронним ядром, перевіряємо завершення та повторний запуск після скасування.
3. **Інтерфейс і відновлення.** Підключаємо форму та інші входи, статуси, скасування, захист від застарілих відповідей; перевіряємо проєкти й пояснення фізичних обмежень.
4. **Приймання.** Виконуємо числові, браузерні й офлайн-перевірки; оновлюємо документацію та готові збірки, записуємо фактичні результати.

## Критерії приймання

| Перевірка | Умова приймання |
|---|---|
| Числові результати | Усі відповідні наявні контрольні тести проходять; перенесення виконання не змінює числові допуски, фази чи альтернативні стани |
| Відгук інтерфейсу | Під час реальної повільної інверсії працюють кнопка скасування та взаємодія зі сторінкою; немає блокування головного потоку всім розрахунком |
| Скасування | Запит припинено, його результат не потрапив у журнал; наступний розрахунок успішний |
| Зміна даних під час виконання | Відповідь попереднього запиту не змінює нові входи, результати, історію чи збережений проєкт |
| Повторні дії | Подвійний запуск, зміна моделі та імпорт під час виконання не створюють дублікатів або неправильних станів |
| Режими й пояснення | Є контрольна матриця 20 режимів; перевірено насичення, критичні стани, альтернативи, фізично неприпустимі входи та відсутні властивості |
| Наскрізний сценарій | Входи й модель зберігаються при передачі в історію, на діаграму, в експорт та після відновлення JSON |
| Офлайн | PWA працює після перезапуску без мережі; відновлення кешу враховує ресурс worker; автономний HTML виконує розрахунок без зовнішніх запитів |
| Доступність | Статуси оголошуються допоміжним технологіям; клавіатура, українська / англійська та ширини 320, 390 і 1366 px перевірені |
| Пакування | Повторна збірка детермінована, ZIP містить усі нові ресурси, перевірки цілісності проходять |

Для сценаріїв гонок допускається керована затримка тестового виконавця; перевірку відгуку інтерфейсу проводимо додатково на справжньому математичному розрахунку. Саме перенесення у worker не означає прискорення числового алгоритму — час виконання вимірюємо й повідомляємо окремо.

Стандартні команди: `npm test`, `npm run verify:water`, `npm run verify:transport`, `npm run verify:release` та нові сценарії скасування/актуальності. Перевіряємо Chromium і Firefox. Відкриття через `file://` перевіряємо в середовищі, де це дозволяє політика браузера; якщо воно заблоковане, результат лишається неперевіреним, і повну готовність автономного формату не заявляємо. Safari та фізичні мобільні пристрої мають окремі результати після фактичного тестування.

## Поза цим спринтом

Нові лабораторні сценарії, реакторна методика, довільний конструктор циклів, нові речовини та фізичні формули, перенесення всіх діаграм і незалежних інженерних модулів у worker. Їхню поточну поведінку контролюємо на регресії, але обсяг фонових обчислень цього спринту — основний калькулятор води й пари.

## Готові матеріали

Код фонового виконавця й інтеграції, регресійні тести, оновлені веб- та автономна збірки, документація користувача й протокол із фактично пройденими, непройденими та неперевіреними сценаріями. Випуск і публікація оформлюються окремо після приймання.

## Фактична реалізація й приймання

`src/calculator-runner.js` керує запитами, помилками, тайм-аутом і припиненням worker; `src/calculator-worker.js` виконує розрахунок та перевірку проєкту. `scripts/build.mjs` збирає чисті залежності ядра, додає версійований ресурс до вебверсії й вбудовує його в автономний HTML. Для Blob worker автономна CSP дозволяє лише потрібний `worker-src blob:`; мережеві підключення лишаються забороненими.

Перевірки проєкту при запуску, імпорті файлу та відкритті з бібліотеки асинхронні. Перевірка всієї бібліотеки при її імпорті, її збереження, графіки та незалежні інженерні модулі зберігають попередній спосіб виконання. Під час стартового відновлення автозбереження вимкнено; якщо користувач змінив роботу, його дані не підміняються відновленим проєктом.

На справжньому пошуку h–v браузерний таймер виконав 52 такти за приблизно 1074 мс у фінальному цільовому прогоні: головний потік продовжував працювати. Це перевірка відгуку інтерфейсу, не прискорення математичного алгоритму.

Оновлені готові файли входять до робочої копії. Машинний протокол: [CALCULATOR_RESPONSIVENESS_ACCEPTANCE.json](CALCULATOR_RESPONSIVENESS_ACCEPTANCE.json). Історичний `RELEASE_ACCEPTANCE.json` стосується попереднього релізу й не є повним прийманням 1.25.0.

## Завершення браузерного приймання

Firefox 153.0 (Playwright 1.62.1) встановлено після застосування мережевих дозволів. Пройдено `calculator-async`, `calculator-workspace`, `smart-input`, `state-comparison`, `study-workflow` та `pwa` у Firefox; фоновий калькулятор і PWA повторно перевірено у Chromium. `test:cross-browser` перевіряє обидва рушії, 28 розділів на ширинах 320/390/768 px, UK/EN, імпорт, експорт, відновлення, діаграми та лабораторний сценарій.

Автономний HTML відкрито через `file://` у Firefox без мережі: розрахунок → порівняння → навчальний звіт, введення й копіювання результатів. Блокування `file://` системним Chromium лишається окремим обмеженням; успіх Firefox його не скасовує.

Тести після перезавантаження очікують відновлені дані, а не лише доступну кнопку. Під час перевірки невдалого відновлення PWA тестовий сервер припиняє відповіді: одного `setOffline()` недостатньо для запитів service worker у Firefox. Перевірки додано до `verify:release`; продуктове числове ядро й збірка не змінені.

Для відтворення: `npx playwright install firefox`, `BROWSER_NAME=firefox npm run test:calculator-async`, `BROWSER_NAME=firefox npm run test:calculator-workspace`, `BROWSER_NAME=firefox npm run test:smart-input`, `BROWSER_NAME=firefox npm run test:state-comparison`, `BROWSER_NAME=firefox npm run test:study-workflow`, `BROWSER_NAME=firefox npm run test:pwa`, `npm run test:cross-browser`. Для сценаріїв, крім PWA, потрібен локальний HTTP-сервер; шлях до браузерного кешу задається через `PLAYWRIGHT_BROWSERS_PATH`. Фактичні журнали: `.release/firefox-responsiveness/`.
