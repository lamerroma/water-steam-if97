# Повне покриття ht і fluids

Дата: 19.10.2026. Статус: вимога до розширення та запропонована архітектура;
runtime ще не інтегрований. Вимога користувача: потрібні всі функції обох бібліотек.

## Обсяг

Ціль — усі публічні розрахункові функції, класи та довідкові дані зафіксованих
версій ht і fluids. Підключення пакета саме по собі не означає завершення покриття.
Поступове відкриття розділів у програмі визначає черговість, а не скорочує обсяг.
Внутрішні службові функції потрібно інвентаризувати як залежності; вони не
обов'язково потребують окремих форм для користувача.

Числове покриття відстежуємо окремо від варіантів виконання: NumPy-векторизації,
обгорток одиниць і прискорення Numba. Їхню сумісність ще не встановлено;
не оголошуємо їх підтриманими через успішний імпорт основного пакета.

Попередній пріоритет Steam97Web зберігається: ця вимога розширює майбутній
обсяг продукту, але не підтверджує відповідність P03/P04 оригіналу і не закриває
наявні відкриті приймальні перевірки.

## Спостережені факти

- На дату перевірки опубліковані ht 1.2.0 і fluids 1.3.1 мають універсальні
  Python wheels. Їхні runtime-залежності включають NumPy і SciPy.
- Обидві бібліотеки мають MIT-ліцензію. Перед включенням потрібні повні тексти
  ліцензій бібліотек і всіх розповсюджуваних залежностей.
- Pyodide підтримує Python wheels і спеціальні WebAssembly-збірки залежностей.
  Це дозволяє досліджувати запуск оригінальних пакетів без перенесення формул.
- У локальному кандидатові 1.36.0 scripts/build.mjs створює тільки багатофайлову
  PWA. Для CoolProp сайт використовує окремий WASM-ресурс.
- Офлайн-ресурси задані у збірці явно; src/service-worker.js також має обмежений
  перелік оброблюваних ресурсів. Нові залежності потребуватимуть змін обох механізмів.
- Поточна політика CSP і спосіб пакування не перевірені з Pyodide.

Повний імпорт, робота API у браузері, обсяг завантаження, пам'ять та час запуску
ht/fluids через Pyodide в цьому проєкті ще не виміряні.

## Запропонована архітектура

1. Зберігати оригінальні пакети з фіксованими версіями та SHA-256. Не створювати
   власну повну JS-копію бібліотек. Оновлення залежностей виконувати явно.
2. Запускати Pyodide в окремому Worker. Ініціалізувати його при першому зверненні
   до нового розділу. Визначити тайм-аути, скасування та відновлення Worker.
3. Зробити адаптер викликів із реєстром дозволених методів. Передавати типізовані
   параметри, масиви й результати; для класів визначити життєвий цикл об'єктів.
   Не підміняти функції з непідтриманими типами приблизними JS-еквівалентами.
4. На межі інтерфейсу явно узгоджувати одиниці, абсолютний/надлишковий тиск,
   молярні/масові величини та безрозмірні аргументи. Зберігати метод, версію
   пакета, вхідні дані й термодинамічну модель у проєкті та експорті.
5. Розповсюджувати повний набір потрібних ресурсів локально із застосунком.
   Для офлайн-режиму не покладатися на встановлення пакетів із PyPI/CDN під час
   розрахунку. Завантаження модуля користувачем і його готовність офлайн мають
   окремі статуси; кешувати та оновлювати узгоджений набір версій.
6. Побудувати каталог усіх методів із пошуком і групуванням. Інтроспекція може
   дати сигнатури, але одиниці, умови застосовності та зв'язані аргументи
   потребують перевірених описів. Для класів потрібні окремі сценарії роботи.

Цільовий формат — багатофайлова вебверсія/PWA. Рішення користувача від
19.10.2026 знімає вимогу запуску всієї програми одним HTML-файлом. Новий модуль
не повинен вбудовувати Python, WASM і пакети в standalone.html або підтримувати
запуск через file://. У кандидатові 1.36.0 однофайлову гілку збірки вилучено;
пакетування та життєвий цикл описано в [архітектурі PWA](PWA_ARCHITECTURE_UK.md).

Перший запуск і завантаження вибраних модулів потребують мережі. Розрахунки
завантажених модулів мають працювати локально після перевіреного кешування всіх
їхніх залежностей. Інтерфейс повинен розрізняти завантаження, готовність офлайн
та відсутні ресурси; сама установка PWA не доводить повноти кешу. Перевірити
квоту сховища, доступність запиту на постійне зберігання та відновлення після
видалення даних браузера. Проєкти повинні мати незалежний файловий експорт.

Якщо частина API несумісна з браузером, записати конкретний блокер і оцінити
інший спосіб запуску оригінального Python; не вилучати цю функцію з цільового
обсягу мовчки. Відмова від одного HTML не усуває обмежень WebAssembly.

## Реєстр покриття та приймання

Для кожного публічного символу реєстр має містити: пакет і версію, повне ім'я,
тип символу, сигнатуру, залежності, одиниці, джерело документації та окремі статуси:

- інвентаризовано;
- імпортується/викликається у браузері;
- перевірено числовий результат і поведінку помилок;
- доступно через інтерфейс із потрібними входами та виходами;
- перевірено збереження/відновлення та офлайн-роботу;
- блокер із відтворюваним прикладом, якщо перевірку не пройдено.

Для базових числових функцій порівнювати однакові версії пакетів у звичайному
CPython і браузері. Перевіряти приклади документації, характерні режими, межі,
масиви та некоректні входи, де це застосовно. Допуски обґрунтовувати властивостями
методу. Таке зіставлення перевіряє інтеграцію, але не є незалежним доказом
фізичної точності самих кореляцій.

Окремо перевірити холодний запуск, повторний запуск без мережі, оновлення кешу,
відсутній/пошкоджений ресурс, скасування та відновлення після помилки. Виміряти
розмір, час запуску й пам'ять на цільових пристроях до рішення про реліз.

## Найближчий технічний етап

Зробити ізольований прототип: оригінальні пакети в браузерному Worker, контрольні
виклики теплообмінника, тепловіддачі та двофазного опору; потім інвентаризація
всього публічного API і перевірка найскладніших типів/залежностей. Три приклади
підтверджують лише працездатність прототипу. Завершення всього модуля потребує
закриття реєстру, а не успішного виконання цих трьох функцій.
