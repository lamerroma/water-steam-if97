# Оптимізація старту — 1.38.1

20.10.2026. Кандидат **1.38.1**, build **f4e75effb80a**.
База порівняння — локальна 1.38.0, build aabf7be9a9ba, коміт 52f445c.

## Підтверджений резерв і зміна

Основний app.js включав незмінений SheetJS 0.20.3 (951 904 байти).
Бібліотека виконувалася під час кожного старту, хоча потрібна тільки для
XLSX/ODS/XLS. Тепер вона розповсюджується окремим версійованим
`assets/sheetjs.js` і виконується при першому відповідному експорті.
CSV використовує наявний власний writer. Node API зберігає синхронну поведінку.

PWA включає файл до основного перевіреного кешу, тому першому експорту без
мережі не потрібна додаткова підготовка. Повторні й одночасні запити ділять
одне завантаження. Помилка або тайм-аут звільняє стан і дозволяє повторити
спробу. Кнопка й формат тимчасово блокуються, вхідний документ фіксується
до очікування бібліотеки. Код сторонньої бібліотеки, алгоритми розрахунків,
допуски, точність і формати таблиць не змінено.

Зменшення основного app.js — **949 919 байтів, 29,89%**. Повний офлайн-набір
практично того самого розміру (+1985 байтів); оптимізація переносить виконання
великої бібліотеки на момент її використання. Це не обіцянка зменшити весь
мережевий трафік або Python-пакет на 30%.

Час і heap — спостереження на одному ПК: Chromium 151.0.7922.34, Node 22.23.3,
нові browser contexts, 7 запусків до й 7 після, локальний HTTP без throttling.
Медіана ready вимірюється при виявленні активної кнопки через Playwright;
це включає затримку опитування, роботу ОС і підготовку PWA. Heap — знімок
JS-пам'яті, не пік і не вся пам'ять процесів браузера. До/після запускали
послідовно; статистичну значущість і швидкодію фізичних мобільних пристроїв
не встановлювали. Універсальний відсоток прискорення з цих даних не виводиться.
Перший binary-експорт тепер оплачує ініціалізацію бібліотеки.

Відтворення поточного вимірювання: `npm run build`, потім
`npm run benchmark:startup -- .release/startup-current.json`.
Потрібен локальний Playwright Chromium. `STARTUP_ROOT` дозволяє виміряти
збережений dist іншої версії; `STARTUP_RUNS` задає 1–50 повторів.

## Перевірки

- **1716/1716** модульних тестів, без пропусків; **17/17** перевірок core release,
  включно з числовими звірками, повторюваністю, пакуванням та ZIP-хешами.
- Chromium і Firefox: по **4 групи** нового `test:lazy-assets` — старт без
  виконання SheetJS; перезапуск профілю з вимкненим сервером і мережею;
  CSV без SheetJS; відсутній ресурс, помилка, відновлення кешу й повторна
  спроба; перший офлайн XLSX/ODS/XLS та один екземпляр завантаженого скрипту.
  Жодних зовнішніх запитів або pageerror у цих сценаріях.
- **8/8** додаткових регресій: P03, P04, повний життєвий цикл PWA та запуск
  із ZIP у Chromium/Firefox. P03/P04 перевіряють також фактичні числові
  значення експорту незалежними читачами таблиць у Python.
- Новий браузерний сценарій включено до `verify:release` для обох браузерів.
  Повний набір усіх браузерних сценаріїв цього разу не запускався.

Ці результати не додають фізичної валідації дослідним моделям і не підтверджують
відповідність Steam97Web. Зокрема, наявний статус нейтронної моделі у core report
залишається physical-screening-failed; повне числове приймання ht/fluids попереду.

## Що досліджувати наступним

У app.js залишаються Chart.js (208 522 байти) та значна частина обчислювальних
джерел, які також потрібні Calculation Worker. Винесення графіків і додаткових
панелей можливе, але потребує вимірювань відкриття цих розділів та збереження
життєвого циклу діаграм, імпорту проєктів і скасування.

Для Python наступна точка профілювання — окремі витрати на старт runtime,
імпорт SciPy й побудову каталогу. Пакет уже завантажується за потреби; бібліотеки
не варто переписувати або змінювати фізичні алгоритми заради припущеної швидкості.
