# Спільний інтерфейс обчислювальних модулів

Протокол версії 1 реалізовано в 1.37.0; у кандидатові 1.38.0 додано ht / fluids
через окремий Python Module Worker. Чинні математичні формули не змінено.

## Реєстр і межі реалізації

`src/calculation-protocol.js` містить незмінний реєстр `CALCULATION_MODULES`,
перевірку протоколу, одиниць, версій, результатів і структурованих помилок.
`src/calculation-modules.js` зіставляє методи з чинними числовими реалізаціями.
`src/calculator-runner.js` керує Worker, тайм-аутом і скасуванням.
Схеми числових входів оголошені в реєстрі через `inputSchemas`: фіксовані
`fields` або `selector`/`cases` для різних вхідних пар. Нормалізатор читає
ці дані; новий метод із наявними величинами не потребує своєї гілки перетворення.

| Модуль | Методи | Формат результату |
| --- | --- | --- |
| `water` | `calculate` | Чинний результат IF97/IAPWS-95 і властивості з одиницями |
| `gas-tables` | `calculate` | Чинний результат BSW2003/VDI4670 і властивості з одиницями |
| `ht`, `fluids` | `catalog`, `describe`, `call`, `get`, `release` | JSON, класи через локальні handles; upstream-документація одиниць |
| `workflows` | `project`, `rankine-sweep`, `study-report-html`, `water-process`, `custom-cycle`, `library-cycle`, `cycle-comparison`, `cycle-preset` | Чинна схема відповідного методу |

Для води підтримані всі 20 наявних вхідних пар, для газів — P–T/P–h/P–s.
Сумісні методи runner (`calculate`, `gasTable`, `readProject` тощо) залишені
для наявного інтерфейсу: вони використовують новий протокол і повертають
оригінальний `result`. Новий `run` повертає повну відповідь із метаданими.

Це реєстр адаптерів поточної збірки. Для ht 1.2.0 / fluids 1.3.1 реалізовано
спільний локальний пакет Pyodide/NumPy/SciPy (~32 МБ) з окремим кешем.
[Виклики та межі підтримки Python-бібліотек](PYTHON_LIBRARIES_UK.md).
Наукові панелі з CoolProp та інші прямі допоміжні виклики поки використовують
наявні адаптери інтерфейсу; їх перенесення в цей реєстр — наступні інтеграції.
Спільна SHA-256 ревізія враховує Calculation Worker, SEUIF97 WASM,
Python Worker, міст JSON та маніфест Python-пакета. Окремий CoolProp WASM перевіряє чинний маніфест ресурсів PWA.
Методи workflows мають спільний транспорт і помилки; їхні фізичні величини
залишаються у чинних схемах. Порожня `quantities` для них не означає,
що результат безрозмірний. Типізувати кожну таку схему потрібно окремим адаптером.

## Приклад виклику

```js
import {createCalculationRunner} from './calculator-runner.js';

// workerURL — URL версійованого Worker з поточної перевіреної збірки PWA.
const runner=createCalculationRunner(()=>new Worker(workerURL));
const controller=new AbortController();
const reply=await runner.run('water','calculate',{
  mode:'pt',a:30,b:100,model:'IF97'
},{
  inputUnits:{a:'bar',b:'C'},
  signal:controller.signal
});

const enthalpy=reply.quantities['state.h'];
// {value: ..., unit:'kJ/kg', status:'available'}
// controller.abort() або runner.cancel() припиняє активний розрахунок.
```

Якщо `inputUnits` не вказані, конструктор запиту явно записує канонічні одиниці.
Якщо вказані — потрібно передати одиницю для кожного потрібного числового входу.
Змішування розмірностей, невідома одиниця, нескінченне число або переповнення
відхиляються до запуску числового методу. Рядки з числами не є типізованими
аргументами: їх розбирає інтерфейс до виклику.

| Величина | Канонічний ідентифікатор входу | Інші підтримані ідентифікатори |
| --- | --- | --- |
| Абсолютний тиск | `MPa` | `kPa`, `Pa`, `bar`, `atm`, `psi` |
| Температура | `K` | `C`, `F` |
| h/u | `kJkg` | `Jkg`, `Btulb` |
| s | `kJkgK` | `JkgK`, `BtulbR` |
| Питомий об'єм | `m3kg` | `ft3lb` |
| Густина | `kgm3` | `lbft3` |
| Частка / сухість | `fraction` | `percent` |

Це ідентифікатори наявного перетворювача одиниць, а не довільні фізичні вирази.
Температурні різниці не приймаються замість абсолютної температури.
Тиск у цих адаптерах завжди абсолютний; явно заявлений манометричний базис
відхиляється. UI перетворює манометричний тиск до виклику, як і раніше.

Для газів використовуються `inputUnits:{p:'bar',value:'C',fractions:'percent'}`
та явний `basis:'mole'` або `basis:'mass'` (типово `mole`). Перетворення
відсотків не змінює базис складу. Наявне ядро перевіряє компоненти, суму часток
і припущення дисоціації. λ передається через `options.excessAirLambda`.
Відповідь явно розділяє `units.inputCompositionBasis` і
`units.outputCompositionBasis`: `result.composition` завжди молярний,
`result.massComposition` — масовий. В `quantities` кожна частка має одиницю `1`
та власний `basis`; опорні T₀ і p₀ мають K та МПа.

## Запит, версії та відповідь

Запит має поля `protocolVersion`, `id`, `moduleId`, `engineVersion`,
`implementationRevision`, `methodId`, `payload`, `inputUnits`.
`createCalculationRequest` формує його для нового API. Поле `type` у викликах
сумісних методів залишено як інформаційний псевдонім; маршрутизація працює
за `moduleId`/`methodId`.

- `protocolVersion` — версія транспортного контракту.
- `engineVersion` — версія адаптера для власних модулів (`1.0.0`),
  фактична зафіксована версія пакета для ht (`1.2.0`) / fluids (`1.3.1`).
- `implementationRevision` — SHA-256 джерел Worker, SEUIF97 WASM,
  Python-адаптера та маніфесту його бінарних ресурсів. Збірка записує однакову ревізію в UI та Worker. Вона змінюється
  при зміні їхніх числових залежностей або адаптерів. Прямі незбудовані імпорти
  для модульних тестів мають `null`; опублікована збірка завжди має хеш.

Невідповідність версії або ревізії дає `version-mismatch`. URL Worker також
залишається версійованим за вмістом. Runner звіряє ідентифікатор, модуль,
метод, версію протоколу, версію адаптера та ревізію відповіді. Відповіді
попереднього завдання/Worker не змінюють поточний результат.

Успішна відповідь містить ідентичність запиту, `status:'ok'`, незмінений
нативний `result`, `model`, `units`, `quantities`, `warnings`, `validity`.
Одиниці результатів явні: МПа, K, кДж/кг, кДж/(кг K), кг/м³ тощо.
Для води шляхи мають вигляд `state.h`, `saturation.liquid.cp`; для газів — `h`,
`cp`, `dissociationDeltaH`. Вихідні числа не округлюються.

`null` зберігається як `{value:null,unit:...,status:'unavailable'}`.
Відсутні поля не вигадуються; нечисловий/нескінченний результат для оголошеної
властивості відхиляється як `invalid-result`. Для дослідної VDI4670 швидкість
звуку й ізентропний показник залишаються недоступними. Рівноважний склад
не обчислюється. Нулі h/s, початковий склад та обмеження моделі збережені
у результаті; газовий адаптер також повертає відлік у `validity.reference`.

`validity` описує область моделі й умови; це не дозвіл використовувати весь
прямокутник min/max. Авторитетними залишаються чинні перевірки ядра,
зокрема фазові межі, критична точка, транспортні обмеження та інверсії.

## Помилки й життєвий цикл

Помилка Worker: `status:'error', error:{code,message,details}`.
`run` і сумісні методи відхиляють Promise з `CalculationModuleError` та
такими ж полями. Відомі коди:

| Код | Значення |
| --- | --- |
| `protocol` | Некоректний запит або відповідь |
| `unsupported-module`, `unsupported-method`, `unsupported-model` | Невідомий модуль, метод/пара або модель |
| `version-mismatch` | Несумісна версія адаптера або ревізія реалізації |
| `invalid-input`, `invalid-units` | Некоректний тип/число/базис або одиниці |
| `invalid-result` | Неочікувана нечислова властивість результату |
| `calculation` | Відмова чинного ядра: область, збіжність або інша його помилка |
| `busy`, `timeout`, `unavailable`, `cancelled` | Стан виконавця |
| `module-missing`, `library-error` | Немає підготовленого Python-пакета або відмова сторонньої бібліотеки |

Повідомлення чинного ядра зберігається дослівно; категорію помилки не вгадуємо
за мовою чи словами в повідомленні. Детальнішу класифікацію таких відмов
можна додати в самому відповідному ядрі.

Один runner виконує одне завдання. `AbortSignal`, `cancel()` і тайм-аут
завершують Worker, що перериває також синхронний пошук. Наступне завдання
створює новий Worker з локальних ресурсів. Обробник AbortSignal знімається
після завершення, щоб пізній abort не скасував наступне завдання.

Python Worker надсилає ідентифіковані `status:"progress"` повідомлення під час
запуску. `run(...,{onProgress})` не завершується на них. `reset()` звільняє
також уже прогрітий Worker; Python handles після завершення Worker недійсні.
Для Python одиниці читаються з upstream docstring без автоматичного перетворення;
непідтверджена одиниця залишається `null`. `numericalAcceptance:"pending"`
відділяє підключення від повного числового приймання.

## Додавання наступної бібліотеки

1. Додати її опис у реєстр: стабільний id, версію адаптера, методи, середовище,
   моделі, схему одиниць та чесний опис підтриманих меж.
2. Реалізувати адаптер без DOM. Параметри передавати типізованими даними;
   вихідні величини оголошувати з одиницями та статусом доступності.
3. Для сторонньої реалізації зафіксувати фактичну upstream-версію, ліцензію,
   атрибуцію, ресурси й SHA-256. Для Python окремо потрібен локальний runtime
   з повним комплектом залежностей; мережеве встановлення під час розрахунку
   не підходить для офлайн-виконання.
4. Підключити метод у dispatcher; важкі залежності ініціалізувати в Worker.
   У поточному етапі Worker ще спільний із SEUIF97; окремі Python Worker
   та їхнє завантаження — наступний етап.
5. Перевірити перетворення одиниць, незалежні числові еталони, відмови,
   скасування, несумісні версії та повторний офлайн-запуск.

Успіх перевірок контракту підтверджує передачу даних і сумісність. Фізична
точність моделей та числовий паритет P03/P04 зі Steam97Web перевіряються окремо.
